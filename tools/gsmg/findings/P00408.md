## Phase 408 -- Bifid period-robustness audit of the BTCSEED checkpoint: full-block-convention-dependent, not disproven (2026-08-25)

**Question:** requested directly by the user as the branch-level gate
before spending further effort on the BTCSEED/P91/Z idea bank's
autokey/second-square items (82-89): does Phase 386's `BTCSEED`
checkpoint survive alternate Bifid block/period conventions, or does it
exist only under the single-570-character-block reading Phase 386
happened to use? Phase 21's earlier period tests do not close this --
they used different decoded-code hypotheses and key families, not Phase
386's exact raw-`FAED`/`DBBI`-keyed construction.

**Method:** wrote
`tools/gsmg/phase408_bifid_period_robustness_audit.py` against a
contract frozen before any code was written: fixed ciphertext (`FAED`,
570 letters), fixed square (`DBIFHCEGAKLMNOPQRSTUVWXYZ`, Phase 386's
`build_grid(DBBI[:13])`), no alternate squares/swaps/reversals/second
passes. 8 labeled block schedules: the 7 standard periods `7, 13, 49,
91, 98, 472, 570` (classical period-Bifid convention -- fixed-size
blocks, final block truncated to the remainder; period 472 naturally
yields `[472, 98]`) plus one custom Z-boundary schedule, `[98, 472]`
(the reverse split-point, deliberately distinct from period 472's
`[472, 98]` since the boundary position determines the output, not
just the block-size multiset). Implemented `bifid_encrypt_block()` as
the true algebraic inverse of Phase 386's own `bifid_decrypt()`
(verified by round trip, not assumed), generalized to block schedules
via `bifid_decrypt_periodic()`/`bifid_encrypt_periodic()`. Per
candidate: SHA-256/first-32-chars, longest common prefix with
`BTCSEED`, exact-prefix/contains checks, `Z` count/positions/uniqueness
at index 97, even/odd rail alphabets and whether the `{B,C,D,E}`-vs-
full-alphabet alternation survives, and character agreement with the
period-570 baseline over the full 570/first 98/final 472. No English
scoring, no blob oracle, no keyword promotion -- this audits the
existing checkpoint rather than searching for a replacement plaintext.
Validation: encrypt<->decrypt round trips required for all 8 schedules
on both the real `FAED` ciphertext and a synthetic `BTCSEED`-prefixed
plaintext (doubling as the required planted positive); period 570
asserted to reproduce Phase 386's `decoded` byte-for-byte.

**Result:** all 8 schedules round-trip correctly (real ciphertext and
synthetic plaintext); period 570 reproduces Phase 386's baseline
exactly. Only period 570 produces output starting with (or containing)
`BTCSEED` -- every other schedule's longest common prefix with
`BTCSEED` is 0-1 characters, pure chance given `B`'s high frequency in
this skewed alphabet. `Z` is uniquely at index 97 only for period 570
(other schedules: 0, 1, 3, or 5 `Z` occurrences, never uniquely at 97).
The `{B,C,D,E}`-vs-full-alphabet rail alternation (`even_is_bcde`)
survives only for schedules built from even-length blocks (`period_98`,
`period_472`, `period_570`, `custom_98_472`) -- a direct consequence of
block-boundary parity, not independent confirmation, since an odd block
size flips which global positions are "even"/"odd" mid-stream. `period_
robust` is `False`.

**Disposition:** descriptive/structural audit, no promotion rule to
trigger. Per the contract's own interpretation rule, the checkpoint is
classified **full-block-convention-dependent** -- not disproven (period
570 is a real, reproducible, independently-motivated boundary: the
entire ciphertext length), but its `BTCSEED`/`Z@97`/alternation package
does not independently reappear under any other tested period or the
custom Z-boundary schedule. Per the user's own stated plan, this
supports parking idea-bank items 82-89 (autokey seeding, deduplicated
second squares, ordered key schedules) unless an independent clue
specifically selects one of those constructions.
