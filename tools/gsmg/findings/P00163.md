## Phase 163 -- creator's own recommended hash-checking tool identified and its exact whitespace behavior tested against the curated corpus: closed negative (2026-08-07)

Follow-on from Phase 155's "two sloppy days... zero polish" retrospective: if
the creator really did assemble this with off-the-shelf tools rather than
custom crypto, the specific tools they're on record using are worth
inspecting for implementation quirks that would silently break an otherwise-
correct passphrase, rather than assuming textbook `hashlib`-style behavior.

**Provenance.** Message `234` in the original puzzle-solvers export
(`ChatExport_2026-07-26`, 2019-04-23) is the creator replying directly to
Doeke's "how to check a password with a hash?" -- asked immediately after
Ewout posted the phase-1 target SHA-256 in message `230` -- with:
`https://passwordsgenerator.net/sha256-hash-generator/`, followed by "or just
get yourself a python script." This is the creator's own recommended method
for exactly the operation this project's AES oracle performs, not an
incidental URL; previously it only existed in this project's wordlists as
the literal candidate string `"passwordsgenerator"` (`chat_mined_words.txt`),
never analyzed as a tool whose behavior might matter. (Phase 1 itself is
already publicly solved -- `theflowerblossomsthroughwhatseemstobeaconcrete
surface`, [doc/GSMG_PUZZLE.md](../../../doc/GSMG_PUZZLE.md) -- so this is a methodological find, not a
live phase-1 gap.)

**What the tool actually does.** The domain no longer resolves (`SERVFAIL`
via Google's DNS-over-HTTPS, confirmed 2026-08-07), but Wayback holds a
capture from 2019-04-25, two days after the message. Its client-side
`calc()`:

```js
if( strTxt.search("\r")>0 ) strTxt = replaceAll("\r", "", strTxt);
var strHash = hex_sha256( strTxt );
strHash = strHash.toUpperCase();
```

is the standard public-domain Paj/Angel-Marin `hex_sha256` (a real, correct
SHA-256, not a broken variant) fed the `<textarea>` value with exactly one
normalization: a literal `"\r"` is stripped if present. Uppercasing the
output is cosmetic. Critically, **no leading/trailing whitespace is trimmed
at all** -- a stray trailing space typed or pasted into the box becomes part
of the hashed string with no warning. (There's also an opt-in "treat each
line as a separate string" checkbox, off by default, irrelevant here.)

**Gap versus existing coverage.** `cb_common.keystr_forms`'s `newline_
variants` flag already covers the "\n"/"\r\n" family (reasoned there as the
"pressed Enter in a terminal" case) -- CR-stripped-CRLF input reduces to
exactly that existing "+\n" form, so the tool's `\r`-stripping adds nothing
new. But no prior form covered a bare trailing space, and `newline_variants`
is off by default in most bulk sweeps for cost reasons (only a handful of
one-off phase scripts opt in) -- so even the newline family isn't uniformly
applied, and the space form didn't exist anywhere.

**Fix and test.** Added `whitespace_variants` as a new, independent,
default-off parameter to `cb_common.keystr_forms` (`form + " "` as one more
base, alongside the existing `\n`/`\r\n` bases when both flags are set) --
purely additive, backward-compatible, verified via `extended_cipher_recheck.
py --self-test` still passing unchanged. New script `password_generator_
whitespace_audit.py` mirrors `extended_cipher_recheck.py`'s existing "Path 1"
discipline (curated candidate lists first, not the raw mined corpora) and
runs the same 648 curated candidates x `answer_forms` x `keystr_forms
(newline_variants=True, whitespace_variants=True)` x `EXTENDED_CIPHER_
VARIANTS` (18 cipher/KDF variants) against all three open blobs (SALPH,
COSMIC, P32TRAILING):

```text
22,716 attempts, 0 hits (real 15m51s, single-threaded)
```

**Curated tier closed for the padded oracle.** 0 hits, as above.

**Second oracle, same gap, also closed at the curated tier.** The other
oracle this project uses for SALPH/P32TRAILING -- `nopad_window_sweep.py`'s
`-nopad` EC-scalar/address-matching path -- builds its keystrings via
`binary_key_material_backfill.normalized_keystrings()`, which also only ever
set `newline_variants=True`, never a whitespace form, at both the curated
tier and the larger `medium_curated_tier1_primary.txt` (24,554 candidates)
it was actually launched against in Phase 94. Added `whitespace_variants`
as an optional parameter to `normalized_keystrings()` (default off, same
additive pattern as the `cb_common.keystr_forms` change above) and a new
`--whitespace-variants` CLI flag on `nopad_window_sweep.py`, threaded into
`run_fingerprint()` as an explicit field (fingerprint version bumped 3 -> 4)
so a whitespace-enabled run can never be silently conflated with a stale
non-whitespace checkpoint. `nopad_window_sweep.py --self-test` still passes
unchanged (the interleaved `RuntimeError`/`ValueError` tracebacks in its
output are the self-test's own deliberate fault-injection cases --
`_worker_init_test_always_fail` et al. -- not a regression).

Ran against the curated 648 (19,402 keystrings, up from 14,551 without the
whitespace form) with `--whitespace-variants --no-bloom --workers 8` into
fresh, separate checkpoint/hits/queue files (no `db/addresses.hash160.bloom`
exists in this environment, so the secondary Bloom-discovery layer was
unavailable -- the primary known-address/vanity checks, which don't depend
on it, still ran at full coverage):

```text
19,402/19,402 completed, 0 errors, elapsed 154.2s (8 workers, ~125 keystrings/sec)
classifications: vanity_strong=1, vanity_weak=1, known=0
```

Zero `known` (exact confirmed-address) hits. The two vanity hits
(`twentythreeciphers` -> `1GSMG1TYZm8L9qgCvfnDPnpBDhB8B1PkcJ`;
`thedemiurge` -> `1GSMG8UMfGFRaxth1tBHTjRDt4yTcNjtjV`) are exactly the kind
of coincidental `^1GSMG[1-9]`-prefix match Phase 95's own base-rate math
predicts will occasionally appear at volume -- neither is the real prize
address (`1GSMG1JC9wtdSwfwApgj2xcmJPAwx7prBe`). Verified live via
`binary_key_material_backfill.py --verify-queue` (Blockstream API): both
addresses are unfunded/never used. Relabeled via `--relabel-vanity-queue`
from the generic `bloom_false_positive` to the correct `unfunded`
classification per Phase 95's convention. Clean negative, independently
confirmed, not just absence of a stronger signal.

**Verdict:** the curated tier is now closed for this specific gap under
*both* oracles this project uses for SALPH/P32TRAILING. Still open: a full
Tier-1 rerun (`medium_curated_tier1_primary.txt`, 24,554 candidates) with
`--whitespace-variants` against the nopad oracle -- not run this phase.
Extrapolating from this run's real throughput (~125 keystrings/sec at 8
workers) and the ~700K-keystring estimate for Tier-1 under the wider form
family, that's on the order of ~90-100 minutes at 8 workers, roughly halving
at 16 (consistent with the oracle's own previously documented ~7.4x
scaling from 1 to 16 workers). Separately, Tier-1/2/3's combined 66,441
candidates have never been run through the *padded* CBC/ECB
`EXTENDED_CIPHER_VARIANTS` oracle at all, in any form (only the curated 648
have) -- a real, pre-existing coverage gap noticed as a side effect, not
part of this phase's scope, and not to be conflated with the
whitespace-specific finding above.

**Disposition note (added 2026-08-22):** the padded `EXTENDED_CIPHER_VARIANTS`
gap above was later closed by Phase 323/328's GPU-oracle backfill of the
same medium-curated Tier 1-3 union (66,433 candidates), negative. The nopad
Tier-1 `--whitespace-variants` rerun remains genuinely unrun; deprioritized
(low expected value -- whitespace variants already tested clean at the
smaller curated tier, and this candidate family has since been superseded
in priority by the medium-curated corpus sweeps), not silently dropped.
