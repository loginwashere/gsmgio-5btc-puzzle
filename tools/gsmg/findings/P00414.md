## Phase 414 -- P32TRAILING blinded independent reconstruction (first panel): closed `protocol_invalid`, no candidate tested (2026-08-25)

**Question:** per Phase 413's own closing note, the next useful bit of
information on `P32TRAILING` is more likely to come from a reader who has
never seen this project's hypothesis history than from another transform
invented inside it. Phase 414 preregistered a self-contained evidence
packet (the confirmed Phase 2/Phase 3/Phase 3.2 plaintext and three worked
calibration examples, nothing else) and a frozen protocol for testing
independently-derived candidate preimages from clean-context solver
invocations.

**Method:** five clean-context `general-purpose` agent invocations were
spawned under the frozen prompt, up to the predeclared 8-invocation cap.
Every raw response was run through the actual `parse_submission()` /
`validate_submission_schema()` / `blinding_violations()` functions, not
inspected by eye.

**Result:** 3 of the first 5 invocations (1, 2, 5) failed schema
validation. All three failures traced to the same field:
`preimage_utf8_hex`, a hand-computed lowercase-hex encoding of the
solver's own `display` string, required with no tool access. Invocation 1
and 2 each left a literal, uncomputed Python expression
(`.replace(" ", "")`) inside that field; invocation 5's hex trailed off
into `"...INVALID"`/`"PLACEHOLDER"` text. A sixth backfill invocation was
separately spoiled by the orchestrator appending an unauthorized
corrective sentence to the frozen prompt -- a distinct protocol violation,
self-flagged and never resolved into a scored submission. No candidate
from any of the 6 invocations was tested against `P32TRAILING`; no oracle
call was made; no evidence packet content, promotion rule, or testing
protocol was invoked on real data.

**Branch (per the frozen five-way interpretation rule):** `protocol_invalid`
-- fewer than 5 eligible, well-formed submissions were obtained within the
8-invocation cap. Per the preregistration's own explicit design, this is
recorded as a methodology note about the invocation procedure, not as
evidence of `P32TRAILING`'s non-identifiability, and does not count toward
a "no convergence" result.

**Root-cause finding:** `preimage_utf8_hex` carries no interpretive
content -- it is a deterministic, non-semantic transform of a value the
solver already stated exactly in `display` (a parsed JSON string has no
inherent whitespace/case ambiguity to disambiguate) -- so requiring
solvers to hand-compute it, without tool access, tested manual hex
arithmetic rather than the derivation reasoning the experiment actually
cares about, at a 50%-ish observed failure rate against exactly this
mechanically-redundant field.

**Interpretation:** this is an instrument defect, not a result about
`P32TRAILING`. The experiment is re-run, corrected, as **Phase 415**:
`preimage_utf8_hex` is no longer solver-provided (this module computes it
mechanically from `display`), and unfinished template residue
(`placeholder`/`todo`/`fixme`/`...`) is now a schema violation in its own
right. The evidence packet, promotion rule, testing protocol, redaction
contract, invocation-identity/cap machinery, and interpretation rules are
unchanged. No candidate, convergence, or closure claim from Phase 414 is
carried forward; Phase 415 draws an entirely fresh panel. Per the standing
exclusions, this branch does not license a new DBBI/FAED combinator, a new
cipher/KDF family, or plaintext generation beyond what the (unchanged)
protocol already licenses.
