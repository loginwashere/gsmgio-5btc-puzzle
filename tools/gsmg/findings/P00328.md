## Phase 328 -- GPU oracle: CBC/ECB/SEED_CBC candidates get the same unconditional raw-key Bloom check stream modes already had; medium-curated 66,433-candidate re-sweep negative (2026-08-19)

**Question:** The GPU oracle's stream-mode (CFB/OFB/CTR) branch already
Bloom-checks every candidate's first two 32-byte chunks as raw private-key
material, unconditionally (independent of the printable z-score gate,
because stream modes have no PKCS7 padding to give a stronger signal). The
CBC/ECB/SEED_CBC branch had no equivalent: a decrypt that passes PKCS7 but
is neither a full-dummy-pad block (Structural, already host-side Bloom/API-
checked) nor printable (Weak/Strong) was silently dropped with hit_kind=0 --
never Bloom-checked at all, even though its first 32 decrypted bytes could
still be a real private key that just doesn't happen to look like English
text. Does closing this gap change anything against the real corpus, and
what does it cost?

**Method:** Extracted the stream branch's existing Bloom-check loop into a
shared `bloom_check_key_chunks` device function (`kernels/aes_kdf_oracle.cu`)
and called it from the CBC/ECB/SEED_CBC branch too, gated on PKCS7 having
passed and the hit being non-Structural (Structural hits keep their existing
host-side full-body check via `keyshape::process_structural_hit`, so this
isn't a duplicate). `BloomChecker::from_hash160_list` (previously
test-only) was un-gated so `selftest.rs` could build a synthetic one-entry
filter. Added `run_cbc_bloom_chunk_check` to the mandatory self-test: a
synthetic AES-256-CBC blob whose body is [private key (32, non-printable) |
8 filler bytes (non-printable) | PKCS7 pad=8 (not 16, so NOT Structural)] --
confirmed the CPU reference sees no hit at all (HitKind::None), then
confirmed the GPU kernel still recovers the key via the new Bloom path.
Passed on the real RTX 5070. A clean (no GPU contention) 4,245-candidate
timing comparison showed the change adds no measurable overhead (221 vs.
222 candidates/sec) -- expected, since it only fires on the ~1/255 of
PKCS7-passing CBC/ECB/SEED_CBC (candidate, variant, blob) triples, far
rarer than the stream branch's unconditional per-candidate check. Re-ran
`medium_curated_all.txt` (66,433 candidates, the same corpus Phase 323/326
already swept) under the default 60-variant AES table with the real Bloom
cache to pick up the newly-added coverage.

**Result:** 588,942 expanded forms, 240 (variant, blob) pairs, 921s (15m21s)
at 640-741 candidates/sec (~110,000-140,000 decrypt+check attempts/sec).
**43 weak hits** (all z-scores 5.00-5.96, right at the threshold -- the same
low-significance noise class every prior sweep at this scale has produced),
**0 strong, 0 structural**. 3 Bloom hits total, all from the pre-existing
stream-mode path (none from the new CBC/ECB/SEED_CBC path), all 3
`confirmed_funded: false` after the mandatory Blockstream API check.

**Incidental finding, not a bug:** diagnosing an apparent slowdown during
this work revealed the pre-existing stream-mode Bloom check (built earlier
this session, before today) had never actually been stress-tested at the
combination of full 60-variant table x full corpus scale x the real
958M-bit Bloom cache -- it is genuinely ~640-740 candidates/sec at that
scale (real EC-point-mult + hash160 cost across the 36/60 stream-mode
variants, unconditional per candidate), not a regression from today's work.
Confirmed via a controlled A/B measurement after also discovering and
cleaning up five zombie Docker containers (from earlier failed `timeout`
invocations against this same command) that were independently
oversubscribing the GPU and making every measurement look far worse than
reality.

**Disposition:** rejected (this candidate universe, under the now-complete
Bloom coverage).

**Facts affected:** none.

**Supersedes/corrects:** none -- extends Phase 322/323's GPU-oracle Bloom
coverage to a gap that existed since the stream-mode check was first added
(undocumented -- see the "Phase 324/325" forward-references in
`Cargo.toml`/`secp256k1_device.cuh` comments, still not written up as their
own FINDINGS.md phase).
