## Phase 164 -- brainstorm item 2: literal page text as a raw (unhashed, undeived) AES/3DES key, curated tier closed negative (2026-08-07)

**Provenance.** Item 2 of a fresh in-chat brainstorm (2026-08-07, prompted
by the same "two sloppy days... zero polish" retrospective framing as
Phase 163 -- this list was generated directly in conversation, not written
to `doc/GSMG_FRESH_BRAINSTORM_2026-08-06.md`): *"Try literal page text as
key material with zero transformation. Not hashed, not derived -- raw
UTF-8 bytes of some already-visible phrase, padded/truncated to key
length."* Flagged at the time as "easy to dismiss as too naive to be the
answer, which is exactly the bias a sloppy-build prior should make you
suspicious of."

**Gap confirmed real before writing anything.** Every sweep in this
project up to this point -- `aes_try_open`/`EXTENDED_CIPHER_VARIANTS`, the
nopad EC-scalar oracle, AES Key Wrap -- treats a candidate string as a
*passphrase*: something run through legacy EVP_BytesToKey, PBKDF2, or a
SHA-256 digest (`keystr_forms`) before it becomes cipher key bytes.
`cb_common.py` already has the complementary half, `raw_key_try_open()`
(zero-IV direct AES/3DES key, no derivation at all, added for AES-Key-Wrap-
unwrapped output) -- but every existing caller (`first_hint_hash_audit.py`,
`youwon_direct_key_derivation_audit.py`, `aes_key_wrap_sweep.py`,
`first_puzzle_announcement_audit.py`) only ever feeds it EXACT-length byte
strings (32-byte SHA-256 digests, key-wrap output). Nothing in the project
had ever taken an arbitrary-length literal string, padded/truncated it to
a valid key length, and tried it raw -- confirmed by grepping every
`raw_key_try_open` call site, not assumed.

**New script.** `tools/gsmg/literal_raw_key_material_audit.py`. Reuses
`extended_cipher_recheck.py`'s existing 648-candidate curated tier (Path 1
discipline) and `answer_forms()` case variants, but deliberately skips
`keystr_forms()` entirely -- no SHA-256, no newline, no whitespace forms --
since bypassing hashing/derivation is the whole point of this check.
`raw_key_forms()` builds one candidate per valid direct-key length
(`RAW_KEY_LENS` union: 8/16/24/32 bytes) via the single most naive
construction a rushed script would plausibly use:
`form.encode()[:n].ljust(n, b"\x00")` -- truncate if longer, zero-pad on
the right if shorter. Each result fed straight to `raw_key_try_open()`
against the three open blobs (SALPH, COSMIC, P32TRAILING).

**Self-test.** Synthetic known-positive vector (a 15-byte phrase
zero-padded to a real AES-128 key, matching `cb_common`'s own
`raw_key_try_open` self-test pattern) confirmed recoverable through the
full `sweep()` path before trusting any negative result:

```text
[*] self-test OK (118 attempts on 6 candidates, 1 hits, synthetic vector recovered)
```

**Real run** (648 curated candidates x answer_forms x 4 key lengths x 3
blobs, deduplicated on exact key bytes):

```text
5,516 attempts, 0 hits (real 0.6s -- no KDF/hashing means this oracle is
essentially free compared to every prior padded-oracle sweep)
```

**Curated tier closed negative.** Given the near-zero cost (no KDF step at
all, unlike every other oracle in this project), immediately extended to
the wider Tier-1/2/3 corpus too rather than deferring it -- added a
`--candidate-file` flag (same convention `binary_key_material_backfill.py`
already uses) and ran directly against `wordlists/gsmg/medium_curated_all.
txt`:

```text
511,342 attempts across 4 raw key lengths x 3 blobs, 0 hits (real 34.8s)
```

**Verdict.** Both the curated 648 and the full Tier-1/2/3 combined corpus
(66,441 candidates) are closed negative for the literal-raw-key
interpretation, in a single phase, at negligible cost (fully single-
threaded, no parallelism needed). Not yet run against the raw mined
corpora (`chat_mined_lines.txt` etc.) -- lowest priority per this
project's existing discipline, and unlike the padded/nopad oracles, cheap
enough that it wouldn't need a time-estimate discussion first if the
raw-corpora tier is ever prioritized.
