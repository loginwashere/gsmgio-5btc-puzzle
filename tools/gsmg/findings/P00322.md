## Phase 322 -- GPU AES/KDF oracle built and validated; creator-authored macro-clue fragment combinations swept: negative (2026-08-19)

**Question:** Could a GPU port of the AES-CBC oracle meaningfully speed up
future password sweeps, and does any order-sensitive combination of up to 7
of the 8 creator-authored macro-clue fragments (the only strings this project
has established as literally the creator's own authored text, not a
solver-derived numeric artifact or third-party movie-quote reconstruction)
open SALPH/COSMIC/P32TRAILING/URLBLOB?

**Frozen inputs:** `promised_standalone_audit.MACRO_CLUE` (8 fragments,
Phase 79/111); `cb_common.py`'s `KDF_VARIANTS` + AES portion of
`EXTENDED_CIPHER_VARIANTS` (4 KDF kinds x 3 AES key sizes = 12 variants); the
4 tracked blobs (SALPH/COSMIC/P32TRAILING/URLBLOB).

**Method:** Checked the sibling `../key-seeker` repo (a mature Rust+CUDA
Bitcoin weak-key tool) for reusable GPU infrastructure -- it has no AES/KDF
code at all (only secp256k1 EC math for a different problem), but its
host-side Rust/CUDA scaffolding (cudarc wiring, build.rs nvcc pattern,
checkpoint/output conventions, GPU launch pattern) was reusable. Built
`tools/gpu_oracle/` (new Rust+CUDA project, full writeup in
[GSMG_GPU_ORACLE](../../../doc/GSMG_GPU_ORACLE.md)): a CUDA kernel implementing
MD5/SHA-1/SHA-256, PBKDF2-HMAC-SHA256, legacy `EVP_BytesToKey`, and
AES-128/192/256-CBC decrypt, gated by the same PKCS7 + printable-z-score +
structural-binary-plaintext logic as `cb_common.py`. Validated via a
mandatory `--self-test` against an independent CPU reference oracle (built
from RustCrypto crates, not a second hand-rolled port): the known-positive
Phase 3.2 vector, and a full negative cross-check across all 12 variants x 4
blobs. `tools/gsmg/macro_clue_permutation_combinations.py` generates every
order-sensitive combination (P(8,k), k=1..7, no repeats -- k=8 deliberately
excluded, reopen explicitly rather than silently including it) of the 8
MACRO_CLUE fragments concatenated directly: 69,280 base combinations,
expanded via `answer_forms()` x `keystr_forms(newline_variants=True)` to
1,247,040 passphrase forms.

**Result:** Self-test passed: GPU reproduced the known-positive vector's
z-score (21.77) exactly matching CPU, and 100% GPU/CPU agreement across the
576-combination negative grid. The real sweep (1,247,040 forms x 48
variant/blob pairs, ~59.9M decrypt attempts) completed in 9m27s on an RTX
5070 (~2,200-3,800 candidates/sec) -- versus an estimated 46min-2.3h for the
equivalent CPU-only run at 8 workers. **Zero hits** -- no weak, strong, or
structural hit anywhere in the space.

**Disposition:** operative (GPU oracle infrastructure); rejected (the
fragment-combination hypothesis itself).

**Facts affected:** none (new bounded exploratory test, not tied to an
existing ledger fact).

**Supersedes/corrects:** none.

**Artifacts:** `tools/gpu_oracle/` (Rust+CUDA project);
`tools/gsmg/macro_clue_permutation_combinations.py`;
`wordlists/gsmg/macro_clue_permutation_combinations.txt`;
[doc/GSMG_GPU_ORACLE.md](../../../doc/GSMG_GPU_ORACLE.md).

**Reopen condition:** the fragment-combination result reopens only if a new
creator-authored fragment surfaces (making it a 9+-fragment space) or if
k=8 (all 8 fragments, one more order of magnitude of permutations) is
deliberately run. The GPU oracle itself remains Phase-1 scope
(AES-CBC only); ECB/CFB/OFB/CTR and 3DES/Blowfish/Camellia/SEED/Key-Wrap are
explicitly deferred, not tested by this phase.
