## Phase 194 -- Cosmic Duality's last-column decode calibrated against a solved blob's identical structure (2026-08-09)

Phase 143 established that reading Cosmic Duality's guide text as a 28x64
Base64 rectangle and decoding the last column gives real, reproducible
structure (`7a20fe...`), oracle-negative as a password/key. What Phase 143
did not test is whether that same texture -- a clean rectangle, an isolated
`0xFE` byte, a below-noise printable ratio -- also shows up when the exact
same operation is run against a blob whose password and plaintext are
already fully solved, which would mean the texture is an ordinary side
effect of OpenSSL's 64-character Base64 line width rather than evidence of
authorial intent.

`data.PHASE32_BLOB_B64` is the only other blob with enough rows for this to
be meaningful: its own Python source literal is already stored as 51 lines
of exactly 64 characters (matching the original README's wrapping, not an
artificial re-wrap for this test) -- SALPH/P32TRAILING/URLBLOB are only 2-3
lines long and too short for a column to carry any signal.

`tools/gsmg/phase32_column_calibration_audit.py` runs the identical
column-extraction/decode used in Phase 143 against `PHASE32_BLOB_B64`:

```
[*] phase32: 51 rows x 64 cols, 38 bytes/column
    last column hex: 4f6319ba40764810ef9f6c7da2057b9bc10b166b486de97d29b282c0b09e49f23042cf48e193
    last column printable: 17/38, z=0.819
    MD5 columns: ()
    FE columns: (19, 21, 31, 32, 42, 52, 53, 58) (observed=8, expected-by-chance=8.84, last_column_has_fe=False)
```

Compared directly against COSMIC's own numbers, recomputed by the same
module rather than re-quoted from Phase 143:

```
[*] cosmic: 28 rows x 64 cols, 21 bytes/column
    last column hex: 7a20fe87aa3e6e3874667fcfc6e8c342545166ce06
    MD5 columns: (32,)
    FE columns: (1, 8, 33, 34, 63) (observed=5, expected-by-chance=5.05, last_column_has_fe=True)
```

Quantifying the FE-column counts against a uniform-random-byte null (each
column is `bytes_per_column` independent bytes; probability at least one
equals `0xFE` is `1-(255/256)^bytes_per_column`, times 64 columns): COSMIC's
5 observed FE-columns against an expected 5.05, and PHASE32's 8 observed
against an expected 8.84 -- both within one column of pure chance. Neither
blob's FE incidence is anomalous, including COSMIC's own last-column FE.
PHASE32 also has zero `MD5` columns and a comparably noise-level printable
ratio.

**Verdict:** a known-solved blob, subjected to the identical rectangle/
last-column operation, produces the same class of output -- an isolated
`FE` byte at a rate matching pure chance, no literal `MD5`, no
above-noise printable signal. This lowers confidence that COSMIC's
`7a20fe...` last column is an intentional secondary encoding rather than an
ordinary consequence of any OpenSSL-wrapped Base64 blob having a
"rectangle" and a "last column" at all. It does not reopen Phase 143's
already-negative oracle result, and it does not rule out that COSMIC's
version is intentional -- it narrows the prior toward "generic byproduct."
Do not re-run row/column operations on any blob's Base64 wrapping without a
new clue specifically selecting one.
