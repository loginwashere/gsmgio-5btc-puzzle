## Phase 162 -- did Phase 161 fetch fresh from Wayback? No -- real gap for 4 files, moot for the other 3, found 7 genuinely new never-checked assets (2026-08-06)

Direct chat question caught a real methodological gap: Phase 161 audited
the repo's already-committed image files without re-fetching from Wayback
first. Checked what that actually means per file, not just conceded the
point:

**`puzzle.png`**: already independently verified byte-identical to a live
fetch (Phase 156, `beta.gsmg.io/puzzle`, `sha256 38125bbd...`). Solid.

**`theseedisplanted.png`, `phase2.png`, `phase3.png`,
`SalPhaseIonCosmicDuality.png`**: genuinely never re-verified against
Wayback -- Phase 5 (this project's original forensic pass) states these
were "pulled fresh from the fork repo," i.e. a community git repo, not
independently fetched. **But re-fetching wouldn't fix this**: per Phase 5's
own established finding, these four are browser screenshots of the
puzzle's HTML pages (URL bar visible in-frame) -- there is no standalone
served image asset for Wayback to have archived in the first place. The
PNG bytes were generated by someone's screenshot tool, not by the creator
or the gsmg.io server, so no fetch method recovers a "more original" copy;
the authoritative source for these pages' actual content is the already-
mirrored HTML (used elsewhere in this project), not the screenshot PNGs.
Stego-testing them was only ever going to bound "did the *screenshotter's*
tool leak anything," not "did the creator hide anything" -- worth stating
as an explicit scope caveat on Phase 161's negative results for these 4
files specifically.

**What the question productively prompted instead**: checking the local
Wayback mirror (`gsmg-site-mirror/img/`, 394 URLs, fetched 2026-07-12) for
genuinely served image assets never examined by any phase. Found several:

- `follow_the_white_rabbit.png` -- confirmed byte-identical to
  `doc/img/gsmg_rabbit_hint.png` (already in Phase 161's sweep). Already
  covered.
- The 8 icon files (`black_banking - war.png`, `blue_ca.png`, etc.) --
  confirmed byte-identical to the already-tested `doc/img/gsmg_icon_*.png`
  copies. Already covered.
- **7 genuinely new, never-checked served assets**: `background-full.jpg`
  (1920x1024), `background-full-1440.jpg` (1440x790, a responsive resize
  of the same image), `bg-tablet-left.jpg` (146x2048), `logo_medium.png`,
  `background-center.png`, `favicon_small.png`, `popup_img_error.png` --
  real site assets, never mentioned anywhere in this project before.

Audited all 7 with `image_stego_metadata_audit.py`'s functions directly:

- All 3 JPEGs: **0 EXIF tags** (consistent with the rest of this project's
  findings).
- **`logo_medium.png` and `favicon_small.png` contain a real `iTXt`
  chunk** -- the first non-empty PNG metadata chunk found anywhere in this
  project's entire image-forensics history (every other image, across
  Phase 5/161/162, has zero). Read in full (not just the truncated
  preview): both are the identical, completely generic Adobe XMP
  boilerplate (`Adobe XMP Core 5.6-c142`, timestamp `2017/07/13-01:06:39`,
  `<rdf:Description rdf:about=""/>` -- genuinely empty, no custom
  properties). Both logo assets share the exact same export timestamp,
  confirming they're from the same branding export batch, not independent
  evidence of anything. Not a hidden message.
- Incidental 2-byte `GZIP`/`BMP` magic-byte matches in 3 of the files,
  checked the same way as Phase 161 (bytes following each hit, hit-count
  vs. filesize/65536 base rate): confirmed noise, not real embedded files.
- No trailing bytes after any `IEND`.

**Verdict:** the fetch-provenance question was worth asking and changed
what got tested -- not by re-fetching the 4 screenshot files (which
wouldn't have mattered) but by prompting a check of the actual mirrored
site for served assets this project had never looked at at all. All
closed negative, but this is now a materially more complete sweep than
Phase 161's, and the screenshot-file caveat is now explicit rather than
implicit.
