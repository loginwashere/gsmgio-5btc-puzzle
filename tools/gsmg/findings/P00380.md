## Phase 380 -- raw-key chunk audit over Phase 378/379's byte-pathway materials: negative (2026-08-23)

**Question:** preregistered during Phase 378/379 review as the strongest
remaining bounded next step: could the right password already be inside
Phase 378/379's 756-material corpus, producing binary secp256k1 private-key
material that this project's ordinary printable-text/structural-binary
oracle gate silently discards? Ordinary key bytes do not look like readable
text, and most target-blob bodies do not match `is_structural_binary_
plaintext`'s narrow (aes, block==16, pad==16, len==64) two-key shape either.

**Preregistered method (frozen before running, unchanged after seeing
results):** corpus = the identical Phase 378/379 756-material set, no new
candidate text or material form. Configurations = the 72 non-Key-Wrap
configurations already run (24 CBC, 12 ECB, 36 stream) -- Key Wrap excluded
since a real unwrap already returns raw key bytes directly (Phase 379's
regression covers its result handling) and has no printable-text gate to
route around. Retention: CBC/ECB keep a body only on a valid PKCS7 pad;
stream keeps every body unconditionally (no validity check exists for
CFB/OFB/CTR); `printable_z_score` is deliberately not applied. Inspection:
exactly the first two 32-byte chunks of each retained body (bytes 0:32,
and 32:64 if present) -- mirroring `doc/GSMG_GPU_ORACLE.md`'s established
"unconditional raw-key Bloom check of the first two 32-byte chunks"
convention, no sliding window. Validity: big-endian value in
`[1, SECP256K1_ORDER)`. Acceptance: an EXACT hash160 match (compressed or
uncompressed) against a frozen 10-address target set -- `PRIZE_ADDRESS`
and `HALVING_ADDRESS` (`first_hint_hash_audit.py`) plus the 8 EC-derived
neighbor hash160s (P+G/P-G/P/2/2P x compressed/uncompressed, ported
byte-for-byte from `tools/gpu_oracle/src/checker/known_targets.rs`, itself
independently re-derived Phase 331/332 from the prize pubkey's 6 real
on-chain spends). No funded-balance gate, no Bloom filter, no live API
call. Stop rule: this corpus and this target set only, no expansion
regardless of outcome.

**Method:** wrote `tools/gsmg/raw_key_chunk_audit.py`, reusing
`binary_key_material_backfill.private_key_details` (this project's one
scalar->address implementation) and `input_byte_pathway_reconstruction_
audit.new_material_forms` (the frozen 756-material generator, unmodified).
A derivation cache keyed by `(kdf_kind, kdf_param, salt)`, reset per
material, avoids redundant PBKDF2(10000) calls across variants sharing the
same KDF group -- cross-checked byte-identical to the uncached per-variant
path via the known-positive Phase 3.2 vector (`PHASE32_PASSWORD`/
`PHASE32_BLOB_B64`) before the real run. Self-test verifies the known-target
set (10 entries; the prize hash160 independently cross-checked against
`known_targets.rs`'s pinned `PRIZE_HASH160` constant, not just this
project's own derivation) and exercises `chunk_check`'s positive path via a
monkeypatched synthetic target (a key of known value, not a real target,
since no real target's private key is known -- that is the open question)
and its negative path (an all-zero chunk, an invalid scalar).

**Result:** self-test passes. Real run: 109,317 bodies retained (valid
PKCS7 pad for CBC/ECB, unconditional for stream) across the 72
configurations x 4 blobs x 756 materials. 218,634 chunks inspected
(essentially 2 per body, since nearly every body is >=64 bytes). **0
hits** against the 10-address known-target set.

**Disposition:** negative for this exact frozen corpus/configuration/
target scope. Closes the specific false-negative surface this audit was
designed for -- a correct password in this material set producing a
binary key the printable-text gate would reject -- for the materials and
configurations already covered by Phase 378/379. It does not extend to
Key Wrap (already returns raw bytes; no printable gate involved), to any
candidate outside the 756-material set, or to any target beyond the frozen
10-address set (e.g. a funded-but-unrelated address, which this audit
deliberately does not check -- that is the GPU oracle's Bloom/API path,
out of scope here per the preregistration).

**Facts affected:** no puzzle fact changes. Adds a new, permanently
reusable coverage class (raw-key-chunk-against-known-targets) that any
future byte-pathway or candidate-material audit in this project can reuse
without re-deriving the target set or the chunk-inspection convention.

**Artifacts:** `tools/gsmg/raw_key_chunk_audit.py`; permanent regression
`test_raw_key_chunk_audit` added to `tools/gsmg/test_recent_audits.py`,
verified passing with no duplicate imports or test names.
