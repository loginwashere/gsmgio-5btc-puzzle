## Phase 519 -- Phase 391's numeric/temporal material widened to all four blobs, closed negative (2026-09-17)

**Question:** Phase 391 froze a 69-material manifest (15 authenticated
milestone numbers x 4 representations, plus 9 literal date/HTTP-date
strings) and, by explicit declared scope, ran it against `P32TRAILING`
only. This is the same "single-blob scope creep" pattern Phase 381 had
(fixed by Phase 517 item 8): does the same manifest open `SALPH`, `COSMIC`,
or `URLBLOB` either?

**Method:** `tools/gsmg/phase519_p391_material_all_blobs_audit.py` imports
Phase 391's manifest and oracle-calling code unmodified and calls its
already-parameterized `run_oracle(blobs=...)` with all four blobs instead
of the default `P32TRAILING`-only set. No new material, representation, or
oracle family is added. Self-test first reproduces Phase 391 exactly
(69 materials, `P32TRAILING`-only, 0 hits) before widening.

**Result:** 69 materials x 4 oracle families x 4 blobs = 33,120 effective
decrypt attempts, **0 hits**.

**Disposition:** closed negative. None of this project's already-
authenticated milestone numbers or dates, in any of the four declared
representations, opens `SALPH`, `COSMIC`, `P32TRAILING`, or `URLBLOB`. No
registered gap closes. This is the second confirmed instance of the
single-blob-scope-creep pattern (after Phase 381/517), closing the one
concrete instance flagged during the 2026-09-17 brainstorm sweep; no other
`P32TRAILING`-only material family has yet been identified as needing the
same widening.

**Facts affected:** none.

**Supersedes/corrects:** none. Extends, does not contradict, Phase 391's
own scoped disposition.

**Artifacts:** `tools/gsmg/phase519_p391_material_all_blobs_audit.py`,
`tools/gsmg/test_phase519_p391_material_all_blobs_audit.py`.

**Reopen condition:** a new authenticated milestone number/date, or a new
representation form, with its own citation -- not a re-run of this same
manifest against the same four blobs.
