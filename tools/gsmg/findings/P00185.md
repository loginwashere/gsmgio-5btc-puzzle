## Phase 185 -- `[23,16,7]` as a direct dbbi/faed position selector, and one non-wrapping cumulative stride walk: both closed negative (2026-08-08)

A brainstorm pass characterized the project's authenticated `[23,16,7]`
chain precisely --
`574061 -> [23,16,7] -> BOTH/ULTIMATELY/THE -> BUT/HYE -> EOL -> Enter/
newline` (Phase 32-34/97) -- and distinguished an authenticated *operand*
from an authenticated *operation*: `[23,16,7]` has three independent
derivations, but nothing independently authenticates "select these literal
positions" or "stride by these amounts" as the intended consumer of that
operand against `dbbi`/`faed`.

**1. Direct literal-position selection, corrected scope.** A first pass
proposed testing `[23,16,7]` as single-character positions into `dbbi` and
`faed` under Phase 33's own four preregistered conventions (forward/
backward, one/zero-based) -- reusing the exact convention set from the
`BUT` derivation rather than inventing a new one. Checking against existing
work first: **Phase 150 already ran the `dbbi` half of this** (single
positions 23/16/7, zero/one-based, forward/reverse, against `dbbi` and the
Phase 3.2.2 plaintext) -- closed negative there already. What Phase 150
did not cover is `faed` (570 chars; Phase 150's index probe was scoped to
the two 91-character inputs). `tools/gsmg/matrixsum_dbbi_faed_position_audit.py`
runs all 8 (2 streams x 4 conventions) anyway, both as an independent
cross-check of the already-tested `dbbi` half and as first coverage of the
`faed` half:

```
DBBI forward_one_based=hhb  forward_zero_based=bah  backward_one_based=gib  backward_zero_based=gcg
FAED forward_one_based=che  forward_zero_based=fhe  backward_one_based=bca  backward_zero_based=idf
```

8 candidates -> 48 materials -> 0 hits. None of the 3-character outputs are
recognizable words (unlike `BUT`'s objective checkpoint), which is itself
weak further evidence against this specific reuse of `[23,16,7]`, though it
doesn't close the operand's relevance to `dbbi`/`faed` under some other
rule.

**2. Cumulative stride walk, narrowed to a single deterministic run per
stream.** The genuinely untested angle Phase 150 didn't cover: repeatedly
advancing by the cycle 23, 16, 7, 23, 16, ... and reading the character at
each running total, instead of reading the three literal positions once.
Flagged before running that "cyclic stride" is not zero-parameter --
start-then-advance vs advance-then-start, wrap vs non-wrap, per-stop
conditions, and independent-decimation vs single-walk readings all produce
materially different outputs, and a wrapping walk in particular has no
fixed stopping rule and shades into an arbitrary permutation family.

Ran exactly one narrowest defensible definition, not a family (per-point
justification in `tools/gsmg/matrixsum_cumulative_stride_audit.py`'s
docstring): authenticated order preserved (23, 16, 7, not reordered),
Phase 33's forward one-based convention reused, advance-first (first
position read is 23, not 0/1), non-wrapping (stop the first time the next
running total exceeds the stream length -- no rotation of the starting
stride), run separately against complete `dbbi` and complete `faed` (no
reversal, no fold). No independent-decimation variant, no wrap variant, no
46-symbol-block reading were run -- explicitly out of scope per the above.

```
DBBI (91 chars):  5 positions [23,39,46,69,85]                      -> "hebgb"
FAED (570 chars): 36 positions [23,39,...,529,545,552]              -> "cdefggefaggccifidaicgeghgediheidfhbi"
```

2 candidates -> 12 materials -> 0 hits.

**Verdict:** both closed negative, reported as exploratory results rather
than calibrated consumers -- neither has an independent output checkpoint
comparable to `BUT`'s "first word after choice" check, and no direct
Phase-3.2 calibration exists for either selector (Phase 3.2's plaintext has
no `dbbi`/`faed`-equivalent substream to rehearse against; `[23,16,7]`
itself remains calibrated only by its three independent prior
derivations). The broader wrapping/rotating/independent-decimation stride
family is deliberately not run: the direct-selector neighborhood is
already partly negative (Phase 150 + here), and expanding the stride
family without new creator-authored "step"/"stride"/"walk" language tied
specifically to `matrixsumlist` or `[23,16,7]` would be the kind of
post-hoc parameter growth this project avoids. That movement-language gap
-- not more selector variants -- is the actual blocker on this avenue.
`test_recent_audits.py` grew to 17 tests, all passing.
